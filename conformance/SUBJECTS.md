# Conformance subjects — measured, not asserted

Every number on this page is generated by `conformance/gen-and-publish.cjs` from an
actual execution of the harness against two builds that differ by **exactly one regex**.
No figure here was typed by hand. A previous revision of this file stated 29/49 and
35/49; both were off by one, which is exactly the failure mode this generation step
exists to prevent.

## What the numbers do and do not say

**The real defect is truncation, not laxness.** Unpatched accepts 24 of
24 over-length addresses and truncates 24 of them. Surplus hex
digits are absorbed into `chain_id`, so **a different account is returned than the one
that was signed, and the network id is invented**. That is a funds-safety bug, not a
strictness preference.

**The fix is partial and the exit codes say so.** Exit is **1 on both** subjects.
15 disagreements remain after the patch. The harness must not be
readable as if the patch made things clean — it did not. The remaining
`rejected-valid` cases are two policy questions (RFC 3986 scheme case-insensitivity,
and surrounding whitespace from QR extraction), not the truncation bug, and they are
listed by id in the harness output rather than summarised away.

## Reproducing

```
node conformance/build-subjects.cjs          # derives both subjects from the published tarball
node conformance/run-against-parser.cjs subj/subject-unpatched.cjs
node conformance/run-against-parser.cjs subj/subject-patched.cjs
```

The runner accepts either a module name or a filesystem path, because the README tells
people to pass a path and `require()` reads a bare string as a package name. That
mismatch made a correct invocation fail with "Cannot find module" and look like a
missing dependency.

`subj/` is generated and gitignored: it is 148KB of someone else's bundled code, and
committing it would make this repository a redistributor for no benefit.
